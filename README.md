# Loom：面向 Agent 产物的推理运行时

Loom 意为织机：经线是固定的接口与编排，纬线是 Agent 产出的 kernel，引擎把两者织成可运行的程序。

---

## 定位

AI Compiler 想做的是把模型图翻译成可执行的程序，难点在于语义鸿沟：图里只有"做什么"，没有"怎么做"。Agent 接手这件事之后，引擎剩下的是运行时与正确性保证，这也是变化最慢、最值得长期投入的部分。

本项目的引擎不做图编译优化、不做算子融合、不做算子生成。它定义接口、负责执行编排与校验。kernel 由 Agent 在离线的 Kernel Harness 中产出，按版本化的 C ABI 接入（当前为未冻结草案）。

Kernel Harness 指用 Agent 编写 kernel 的那套系统：把模型转成 plan，驱动 Agent 产出 KernelUnit，跑校验与调优，最后打包。它需要理解模型语义，因此被放在运行时之外。

---

## 三个核心判断

第一，TVM 的问题在于抽象层次选错了，不在工程能力。

它把 warp、pipeline、schedule 这些每隔两三年就要更新的概念，写进了本该稳定的抽象层。Hopper 引入 TMA、WGMMA 和 warp specialization 之后，这套原语既无法表达新机制，也难以统一新旧机制。由此得到的结论是：接口应当放在硬件特性变化最慢的层次上。`kernel<<<grid,block>>>(args)` 这组概念沿用了将近二十年，而 wgmma 之类的概念只活了三年。

第二，困难在"图到程序"的语义鸿沟，而这个鸿沟不该由引擎填。

图里只有"做什么"。补上"怎么做"需要搜索和创造，那是 Agent 的工作，而且应当放在离线、可重试、可人工复核的地方。

第三，引擎理解数据流，不理解语义。

它知道某个 slot 被哪个 node 写入、被哪个 node 读取，不知道那是一次卷积。这条边界让引擎的规模停止增长：功能需求会不断出现，但资源管理类的需求是有限的。

## 十个关键设计决策

| 序号 | 决策 | 理由 |
|---|---|---|
| 1 | 不做图编译，不做算子生成 | 属于代码生成，交给 Agent 与 Kernel Harness |
| 2 | KernelUnit 等于一个 `.so` 加一个入口符号 | 失败隔离、arch 分离、可签名 |
| 3 | ABI 只承认缓冲区、参数、workspace 和 stream | 这是十几年没有变化的抽象层次 |
| 4 | grid 与 block 由 KernelUnit 的 launcher 在调用时计算 | 符号化 kernel 才可能，形状组合才不会爆炸 |
| 5 | plan 分离执行 DAG 与 schedule，依赖由声明推导 | 默认确定性拓扑排序，显式 schedule 必须满足依赖 |
| 6 | 结构由确定性程序生成，只有 kernel 实现交给 Agent | LLM 只应做有客观判据的工作 |
| 7 | 厂商库是 KernelUnit 的一等公民 | 不在 cuDNN 最强的领域硬拼 |
| 8 | 每个 KernelUnit 必须有 ref 实现与降级路径 | 始终可运行，且 ref 是校验的 oracle |
| 9 | 数值契约、误差预算与任务指标由应用方和离线验证工具确定 | 分开验证实现正确性与模型质量，隐藏测试降低过拟合风险 |
| 10 | 硬件特化必须声明，并在加载时检查 | 否则会在 A100 上执行 H100 生成的代码 |

## 现在的状态

设计仍在验证中，ABI 与 plan 尚未冻结。C++17 原型已实现执行 DAG 校验、确定性调度、静态 tensor 描述和入口契约匹配；显式启用实验选项后，可通过 C ABI 加载 CPU 动态库，同步运行两个独立编译的算子，管理输入、权重、输出和 workspace 生命周期。尚未接入模型包和设备后端。构建方式与支持范围见 [16 实现起点](docs/16-implementation.md)。

下一步是 11 文档中的验证期，约三到四周，先弄清这条路在哪里走不通，再决定是否投入半年：

- E1：做一个语义无关的执行器加手写融合 kernel，看声明负担是否可接受
- E2：让 Agent 写五个算子，看真实水平
- E3：访谈八个团队，看需求是否存在

验证期的三个实验，任何一个失败都应当导致改写，而不是硬推。

## 与 infer_history.md 的关系

本蓝图是对 `infer_history.md` 的展开。

那份文档给出了三条关键判断：算子是一个程序而不是一条指令；TVM 的抽象在 Hopper 之后失效；"多模型乘多硬件"是伪需求。本文档接受这三条，并补上了原作没有展开的部分：

| 原作有的 | 本文档补的 |
|---|---|
| 对 AI Compiler 的诊断 | 替代方案的具体形态：接口约定、运行时与校验 |
| "引擎该做稳定的部分" | 哪些是稳定的，用 S0 到 S3 分级和抽象层次判据给出 |
| "Agent 生成算子要符合接口规范" | 规范的具体内容：ABI 头文件、manifest、plan 格式、验收协议 |
| 判断 | 可以执行的验证实验与阶段门禁 |
| — | 最强的反面意见与失败情形推演 |

有一处收紧：原作隐含"Agent 生成一切"。本文档把它限制为 P5，即结构由程序生成、kernel 由 Agent 生成。原因是 LLM 只应被放在有客观判据的位置上。
