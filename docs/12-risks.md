# 12 风险与反面意见

本文整理自一次独立的红队评审。目的是把最强的反对意见完整记录下来，并对每条标明处理程度，而不是只写对自己有利的部分。

处理程度用文字标注：

- 已解决：架构层面有明确答案，质疑在当前设计下不成立。
- 部分解决：有对应机制，但成本或残余风险真实存在。
- 接受：承认这是弱点，靠调整定位或准备预案应对，不打算在工程上消除它。

---

## 1 十项质疑

### 质疑 1：内存管理与融合语义强耦合，引擎无法独立完成分配

质疑：一旦做融合，中间 buffer 消失、workspace 需求变化、布局沿计算链传播、tiling 依赖 shape。引擎若不懂语义，就无法判断 in-place 与 alias 是否安全，只能退化成只会按声明执行的组件。而 bn、act、concat、upsample 这类访存型算子常占检测网络端到端时间的 30% 到 50%，这部分收益正是靠融合感知的 buffer 复用拿到的。

回应：这个质疑成立的前提是"优化必须在运行时发生"。在本设计中，全局分配发生在 Kernel Harness：Kernel Harness 能看到完整语义，可以做任意智能的分配，产出的结果写进 plan 的显式内存计划（`05-plan.md` 第 6 节）。引擎只负责验证，验证用的是四条纯数据流规则：区间是否重叠、是否越界、对齐是否满足、alias 关系是否自洽。四条都不需要语义。

alias 关系由生产者声明（`04-abi.md` 第 10 节的 `inplace_ok` 与显式视图 slot），引擎校验声明的自洽性。所以融合感知的 buffer 复用确实存在，只是它在 Kernel Harness 里，不在引擎里。

残余风险是真实的：声明负担。每个 kernel 要声明读写集合、workspace 公式、是否允许原地、对齐要求。如果这个负担导致频繁出错，收益会被调试成本吃掉。缓解方式是声明由 Kernel Harness 从 manifest 生成而不是手写，并在 debug 模式下做"声明与实际行为"的偏差检测。

结论：部分解决。验证实验见 `11-roadmap.md` 的 E1。

---

### 质疑 2：Agent 生成的 kernel 打不过库，价值主张归零

质疑：用 Triton 写 conv 普遍比 cuDNN 慢 1.5 到 3 倍，要追平必须下沉到 CUTLASS 或 PTX。而 conv 恰好是 cuDNN 十年 autotune 积累最厚的地方。

回应：这个质疑是对的，但它攻击的是一个我们并不持有的主张。

公开数据支持它：KernelBench-Verified 上最好的单轮几何平均只有 0.88 倍；Kevin 报告的 1.10 倍是对 PyTorch eager，不是对 cuBLAS（见 `14-related-work.md` 第 1 节）。

所以本设计从不主张"Agent 要打败库"，而是主张让 Agent 决定哪里该用库、哪里自己写（`01-principles.md` P16）。孤立的 3×3 conv 直接用 cuDNN，Agent 只需判断这里不该自己写；C2f 这类融合块没有任何库提供现成 kernel，基线是三个独立 conv 加三次写回，Agent 赢的是融合本身。

`10-yolo.md` 第 4 节把这一点落实成具体数字：三十个 KernelUnit 里只有八到十个需要 Agent 自写，这也把 M1 阶段的工作量从三十个降到十个。

残余风险是 Agent 可能过度自信，在 cuDNN 更强的场合坚持自写。缓解方式是在生成流程中强制先评估 vendor 方案，并用 E2 实验给出明确的取舍阈值。

结论：已解决，因为它被转化为定位问题而非技术问题。

---

### 质疑 3：YOLO 与 CNN 是萎缩的低垂果实，性能上限已被钉死

质疑：检测模型算子不到二十种，TensorRT 的整图融合加 tactic 选择已经做到极致，真实瓶颈常常在后处理与多路调度。赢了无法证明价值，输了立刻出局。

回应：接受。这一点在 `10-yolo.md` 第 2 节已经明确写出。

定位是：YOLO 用来证明机制成立，不用来证明商业成立。作为试验场，它的优点无可替代——结构已知、有客观指标（mAP）、有强基线（TensorRT）、融合空间真实、可以拆成三十个独立单元。作为市场，它确实不是好选择。

结论：接受。

---

### 质疑 4：只做稳定层等于做一个已商品化的 runtime，没有竞争壁垒

质疑：内存池、stream 与 event、graph executor、动态形状，ONNX Runtime、IREE、TVM runtime、vLLM 都开源免费且更成熟。你把差异化外包给 Agent，把成本留给自己。

回应：部分成立，需要重新定义竞争壁垒。

竞争壁垒不是 runtime 代码，这部分确实会被商品化。可能形成积累的是三样东西：

| 资产 | 为什么难复制 | 是否随规模增长 |
|---|---|---|
| 契约与校验规则库 | 每条规则对应一次真实事故 | 是 |
| 已验证的包语料库 | 只增不减，是 ABI 兼容性与回归的基准 | 是 |
| Kernel Harness 的语义决策质量（布局传播、融合分组、成本模型） | 需要真实模型与真实硬件的反馈才能调好 | 是 |

但必须承认：这三样都需要部署量才能积累。冷启动阶段，我们确实只是"一个更好的 runtime 加一个 Agent Kernel Harness"，而这两者都可被替代。

缓解方式：第一版不要指望靠 runtime 卖钱，要么靠服务（把模型在目标硬件上做到最优），要么开源。

结论：部分解决，竞争壁垒的定义需要随时间验证。

---

### 质疑 5：按（模型，硬件）组合做 Agent 定制，是成本更高的 M×N

质疑：编译器至少能静态摊销；Agent 每个组合都要跑生成、编译、验证，成本是 O(M×N) 且不可复现，绑定 prompt、模型版本与采样。GPU 大约两年换代一次，全部要重做。

回应：这是本项目最真实、也最接近致命的质疑。只能部分回答，无法完全化解。

三个可用的杠杆：

1. 厂商库优先把工作量压到三分之一。`10-yolo.md` 第 4 节显示三十个 KernelUnit 里只有八到十个需要生成。
2. KernelUnit 复用。conv_bn_silu、concat、upsample、sppf 在模型之间可以复用，registry 按语义签名、shape 类别和硬件索引。
3. 保留源码即可重编译（`06-package.md` 第 2 节）。硬件换代时做的是重编译（分钟级），而不是重新生成（小时级），只有调优参数可能需要重搜。

但这些都回答不了"成本是 O(M×N)"这个结构性事实。能做的只是把常数压得很低，而不是把复杂度降到 O(M+N)。

所以结论要写清楚：本方案只在"（模型，硬件）组合数少，但每个组合价值高、生命周期长"的场景下经济成立。如果目标是支持任意模型乘任意硬件、边际成本趋近于零，那是编译器的目标，本项目做不到。

结论：部分解决，是项目最需要关注的风险。

---

### 质疑 6：用 ABI 规范 Agent 产出是幻想，难点在 layout、精度和边界约定

质疑：锁死 layout，Agent 就失去了融合 transpose 的空间；放开 layout，引擎又无法规划内存与校验。ONNX 的语义已经足够规范，layout 不匹配仍然是推理引擎一半 bug 的来源。

回应：这里混淆了两个概念：规范和声明加校验。

ABI 从不规范 layout，它只做一件事：携带一个 layout_id 整数（`04-abi.md` 第 4.6 节）。layout 的决策在 Kernel Harness，由全局传播算法完成，可以任意智能；layout 的一致性由 Kernel Harness 的确定性合成器保证，因为它同时生成 slot 的 stride 和 node 对 layout 的期望；不一致时由校验发现——kernel 声明 `required_layout`，不匹配就报错，不会静默。

所以"锁死"与"放开"这个二选一是伪困境：layout 可以自由选择，但必须被声明，声明不一致会被抓住。

残余风险是真实的：Kernel Harness 的布局传播本身是一个有实质难度的问题（图着色加代价模型），做得不好会插入大量 transpose，这部分不会免费得到。

结论：部分解决。

---

### 质疑 7：只有局部融合权，拿不到全局最优

质疑：检测网络的主要收益来自全链 layout 传播、跨层 buffer 复用（concat 与 upsample 的 ping-pong）、多 stream 重叠。Agent 给局部方案、引擎贪心执行，结果是单算子快、端到端慢。

回应：与质疑 1 是同一个答案，这些都属于 Kernel Harness 的职责：

| 收益来源 | 执行者 | 位置 |
|---|---|---|
| 全链 layout 传播 | Kernel Harness `layout/` | 离线，全局 |
| 跨层 buffer 复用 | Kernel Harness `mem/` | 离线，全局分配 |
| 多 stream 重叠 | plan 中显式声明 | 离线决策，引擎执行 |

引擎不做任何贪心决策，它按 plan 执行，而 plan 是全局决策的结果。

残余风险是：Kernel Harness 要真的做出全局方案，而不是逐层贪心。这是能力问题而非架构问题，但需要投入。

结论：已解决，前提是 Kernel Harness 的全局优化能力到位。

---

### 质疑 8：校验是持续对抗的问题，不是跑一遍 diff

质疑：fp16 和 INT8 下"等价"没有定义，需要逐算子误差模型。容差松了放过 bug，紧了误杀，Agent 会精确卡边界。GPU 侧隔离（越界写、死锁）只有 MIG 和时间片这类手段，成本高且不完整。验证会吃掉一半工程量，而用户不会为校验器付钱，却会因为一个错误的 kernel 丢掉客户。

回应：全部成立。做法是把它做深，而不是假装它简单。

| 质疑点 | 处理方式 | 位置 |
|---|---|---|
| 等价没有定义 | 目标数值契约由独立参考验证；应用方预算与留出数据确定验收规则 | `09-runtime-services.md` 第 5.2 节 |
| Agent 卡边界 | 比较规则随验证产物版本化，Agent 不可修改；发布留出样本不公开 | `07-agent-protocol.md` 第 10 节 |
| 只测分布内 | 六种输入分布，加覆盖域全形状扫描 | `09-runtime-services.md` 第 5.3 节 |
| 少算或漏算 | 依赖探针：扰动每个输入元素，输出必须有响应 | 同上 |
| 越界写 | canary、对齐扰动，可选 sanitizer | `09-runtime-services.md` 第 2.3、2.4 节 |
| 显存回退 | 峰值显存核算，超过 ref 的 110% 判失败 | `09-runtime-services.md` 第 5.3 节 |
| 隔离 | 承认做不到：GPU 无法中断 kernel，只能检测并让设备上下文失效 | `09-runtime-services.md` 第 7.3 节 |
| 工程占比 | 明确预留 30% 到 40% 的工程量 | `11-roadmap.md` |

残余风险：逐 node 校验通过不等于端到端指标达标，误差会沿链传播，可能放大也可能抵消。所以必须有任务级门禁（mAP），不能因为逐 node 全绿就放行。

结论：部分解决。这里放弃了"证明 kernel 正确"的目标，改为以高概率、低成本、可定位的方式发现错误。

---

### 质疑 9：产物不可复现，加上硬件换代，投入摊销不回来

质疑：产物绑定 prompt、模型版本和驱动，回归时无法二分定位；新架构一出，按硬件做的调优全部作废。

回应：

| 子问题 | 处理方式 |
|---|---|
| 不可复现 | 产物按内容寻址且不可变（`06-package.md` 第 10 节）；生成时固定 seed，记录 prompt hash 与工具版本 |
| 回归无法二分 | 每次状态转移落盘产物，CI 保留最近三十次 |
| 硬件换代作废 | 保留源码，换代时重编译（分钟级）而非重新生成（小时级），只有调优参数需要重搜 |
| 旧包不可用 | 指纹显式拒绝加载，同时提供名称相同的新版本包；ABI 语料测试保证引擎不破坏兼容 |

残余风险是重调参成本。一个在 sm_90 上调到 120 个寄存器的 kernel，在下一代架构上可能需要重新调 tile。这部分无法消除，只能把成本估到首次生成的 20% 到 30%。

结论：部分解决。

---

### 质疑 10：工作流没有归属，AOT 太慢而 JIT 太贵

质疑：编译期执行意味着用户要等几分钟到几小时，且没有性能保证；运行期执行意味着引擎里塞 LLM 调用，延迟、成本和可靠性都会出问题。

回应：本设计明确规定这是 AOT，且引擎内绝无生成（P14）：

```
生成（小时级） → 打包 → 注册 → 部署（毫秒级加载） → 运行（微秒级开销）
  离线、一次性        产物冻结、不可变        与 Agent 完全解耦
```

用产品语言说：生成是一个构建步骤，不是运行时行为。就像不会在用户请求时运行 gcc。

残余风险是首次生成一个新组合的等待时间（小时级），在"紧急上线新硬件"的场景下不可接受。缓解方式是预生成常见组合，同时允许先跑符号化 kernel 版本（当天可用，性能次优），后续替换为 tuned 版本。

结论：已解决。

## 2 三个被低估的问题

### 2.1 动态形状可能把 Agent 逼回编译器

问题：融合决策与 tiling 参数都依赖 shape。AOT 按 bucket 生成会导致组合爆炸（batch 1 到 32 乘五档分辨率共 160 种），而 JIT 的生成延迟不可接受。

回应：这是本设计最有技术含量的一处取舍。与 IREE 的关键差异在于（`14-related-work.md` 第 3.1 节）：IREE 的 `hal.executable.export` 在编译期固定 workgroup size 与 count，而我们把 grid 与 block 的计算放进 KernelUnit 自己的 host launcher，在调用时计算（`04-abi.md` 第 1 节，决策 0008）。

后果是符号化 kernel 可以一个 KernelUnit 覆盖所有 shape，代价是性能损失 5% 到 15%；热 shape 再单独做 override。形状组合从"160 套"降到"1 套符号化加 3 套特化"。

残余风险：符号化 kernel 的 launcher 每次调用要重算 grid（1 到 3 微秒），且某些优化（例如固定 tile 下的寄存器分配）在符号化下做不到最优。这正是要保留热 shape override 的原因。验证方法是 E1 中同时测量符号化版本与特化版本的差距，若超过 20% 说明代价过高。

### 2.2 校验需要可执行的数值语义

已在质疑 8 中处理。逐节点观测误差不是普适误差上界，量化和低精度舍入也不能统一由 FP64 替代。需用符合目标数值契约的独立参考做局部验证，再用原始模型基线和任务指标评估端到端质量。

参考执行器若不支持某个契约，需要补参考或标记未验证，不能仅靠放宽容差或通过任务指标就宣称 kernel 正确。样本覆盖不足仍是残余风险。

### 2.3 性能归因才是 Agent 迭代的关键

问题：端到端慢 15%，究竟是 launch 开销、bank conflict、L2 thrash 还是 stream 同步？NCU 有开销且不直接解释原因。没有可靠归因，Agent 的优化就是稀疏奖励下的随机游走。

回应见 `09-runtime-services.md` 第 6 节。

1. 由 manifest 声明 roofline 元数据（纯数字），引擎直接计算 FLOPS 与带宽利用率，不需要 NCU 就能区分访存受限、计算受限和延迟受限。
2. 用规则表把"相邻 kernel 间隙大""最后几个 node 占比高"这类信号翻译成可行动的诊断。
3. 承认 NCU 不可替代：寄存器溢出、bank conflict、L2 命中率只有它能给出。所以观测模块要预留 NCU 集成接口，能导出可复现的命令。

## 3 失败情形推演

如果项目失败，最可能的路径如下。

```
M0 到 M3（第 1 到 7 月）
  运行时做出来了，YOLOv8n 跑通，性能与 ONNX Runtime 持平。
  团队判断"价值在 Agent 层，引擎只是使能器"。

M4（第 8 月）
  接入 Agent 做融合。由于引擎不懂语义，被迫让 Agent 回传越来越多的声明，
  接口持续膨胀，第一次架构裂缝出现（本设计中质疑 1 的残余风险）。

M5 到 M6（第 9 到 10 月）
  实测 conv 比 cuDNN 慢 1.4 到 2 倍。归因为"prompt 不好"或"Triton 不行"，
  转向让 Agent 写 CUDA 加 CUTLASS 模板。kernel 数量从 8 个涨到 60 个，
  验证矩阵爆炸（60 乘形状乘精度）。

M7（第 11 月）
  客户 POC 要求 INT8、动态 batch、多路视频。
  Agent 产出的 kernel 在 scale 传播和 dynamic tiling 上同时出错，
  现场演示检测框全错；由于采样随机且未固定模型版本，无法复现。客户流失。

M8（第 12 月）
  维护成本被确认为 O(模型 × 硬件 × 精度)，产物半年失效。
  定位从"AI Compiler 替代者"降为"YOLO 加速外包"。

M9
  核心工程师因长期写衔接代码和调 prompt 离职，项目终止。
```

根因落在 M5 到 M6 的性能实测：两边都不成立——Agent 打不过库，引擎又不敢做融合。

针对这个剧本，本设计有三处对应安排：P16（厂商库优先）消除"两边都不成立"中的一头，我们不需要打败 cuDNN；P15（语义优化放 Kernel Harness）消除 M4 的接口膨胀，语义留在 Kernel Harness 不回灌引擎；质疑 8 的处理（容差标定加产物不可变）消除 M7 的复现失败。

但这三处安排本身都需要工程量，且都可能在进度压力下被放弃。剧本的价值不在于"已经防住"，而在于知道压力会从哪里来。

## 4 风险清单

| 风险 | 可能性 | 影响 | 早期信号 | 应对 |
|---|---|---|---|---|
| 声明负担过重，调试成本吃掉收益 | 中 | 高 | plan 中手写字段变多，调试时间超过生成时间 | 声明由 Kernel Harness 生成；偏差检测 |
| Agent 在库更强的场合坚持自写 | 高 | 中 | 自写 conv 性能低于库的 0.9 倍 | 强制执行 vendor 评估步骤 |
| YOLO 场景没有商业价值 | 高 | 中 | E3 访谈结果 | 定位为试验场，市场另选 |
| runtime 被商品化，没有竞争壁垒 | 高 | 高 | 客户问"和 ONNX Runtime 有什么不同" | 不做 runtime 生意 |
| 按组合的成本无法摊销 | 中 | 致命 | M4 复用率低于 30% | 转 Plan C（见 `11-roadmap.md` 第 9 节） |
| Kernel Harness 布局传播质量差，transpose 过多 | 中 | 中 | plan 中 transpose 占比超过 15% | 布局传播的代价模型与单测 |
| 校验工程量超出预算 | 高 | 高 | M2 时校验代码占比超过 50% | 预留 40% 预算，分级校验 |
| 硬件换代后重调参成本高 | 中 | 中 | 首次跨架构迁移超过一周 | 保留源码，自动化重编译 |
| 首次生成延迟不可接受 | 中 | 中 | 客户要求新硬件当天可用 | 符号化版本先上线 |
| Agent 产物带来供应链安全问题 | 中 | 致命 | 客户安全评审提出异议 | 沙箱、签名、溯源、许可扫描（P12） |
| 许可污染（Agent 记忆出 CUTLASS 代码） | 中 | 高 | 许可扫描告警 | pack 阶段强制扫描并阻断 |

供应链安全这一项需要单独说明：Agent 生成的 kernel 是任意代码。在企业客户的采购流程中，"我们会 dlopen 一个 LLM 生成的 .so"这句话一定会触发安全评审。没有沙箱、签名和溯源三项措施，这个项目进不了任何合规环境。

## 5 适用范围

明确写出不适用的场景，比只列适用场景更能建立信任。

| 场景 | 是否适用 | 原因 |
|---|---|---|
| 通用推理平台，支持任意模型与硬件 | 不适用 | 那是编译器的目标 |
| 模型频繁更换（研究或实验阶段） | 不适用 | 每个模型都要特化，成本不划算 |
| LLM 推理服务 | 第一版不适用 | 瓶颈在调度与 KV 管理，不在算子 |
| 单一模型配单一硬件，长期运行 | 适用 | 特化成本可摊薄 |
| 需要可审计、可复现、可解释的部署 | 适用 | 契约与产物冻结是天然优势 |
| 边缘设备，Kernel Harness 受限（无 Python、无编译器） | 适用 | 纯 C++ runtime 加预编译包 |
| 新硬件刚上市，厂商库还不成熟 | 适用 | Agent 可以先出可用版本，库成熟后替换 |
| 追求比 TensorRT 快 30% | 需谨慎 | 不承诺。合理目标是持平到快 10% |

## 6 最需要关注的风险

技术上的问题大多有降级路径：契约守不住可以退成半个编译器，Agent 写不好可以让人来写，商业不成立可以退成 kernel CI 工具。唯独成本模型没有降级路径。

如果无法把"每个（模型，硬件）组合"的边际成本压到天级，这个项目就只是一个精致的手工作坊，无法规模化。

因此 `11-roadmap.md` 中 M4 的两个指标——第二个模型两周内完成、KernelUnit 复用率不低于 50%——不是加分项，而是判断项目是否成立的主要依据。
