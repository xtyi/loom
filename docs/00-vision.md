# 00 背景与设计判断

本文说明这个项目为什么采用现在的设计，边界划在哪里，以及在什么条件下这套设计会失效。后续文档中的具体决策都可以追溯到这里的判断。

---

## 0.1 三个已经失效的前提

`infer_history.md` 描述的演进过程，可以归结为 AI Compiler 依赖的三个前提。这三个前提今天都已经不成立，但主流推理引擎的实现仍然建立在它们之上。

### 前提一：op 可以当作指令处理

原文的说法是："很多人把模型中的一个 tensor add 对标 cpu add 指令，这是严重的错误。"

一个 tensor op 是一个完整的程序，涉及迭代空间划分、分块、访存层次、并行映射、同步和流水。CPU 编译器的输入已经把"怎么做"写清楚了；GPU 编译器的输入只有一个函数名。因此，从图到程序不是一次翻译，而是一次合成，而合成所需要的信息并不在图里。

这个判断的直接后果是：不借助搜索、调度模板或人工经验的、只读取图的编译 pass，无法完成这一步。TVM、TensorRT、XLA 都在这个鸿沟上做近似，代价是引入搜索空间、手工调度模板和专家规则。这三样东西都会随硬件代际快速失效。

### 前提二：存在一套能长期承载硬件演进的中层 IR

TVM 把 warp、thread、共享内存、pipeline 这些概念写进了 IR 和 schedule 原语。Hopper 引入 TMA、WGMMA、warp group、mbarrier 和 warp specialization 之后，这套原语既没有位置表达新机制，也无法把新旧机制统一抽象，结果只能重写。

由此得到一个可推广的判断：一个抽象层能活多久，取决于该层次上硬件特性的变化周期。

### 前提三：算子生成必须是引擎的内建能力

这是整个领域默认接受、但很少有人明确写出的前提：既然算子写不完，引擎就应该自己会写。

算子生成本质上是一个合成问题，需要领域知识（分块、访存、硬件机制）、搜索、试错，以及读懂编译错误和 profiler 数据的能力。这些恰好是 Agent 擅长的，而且这个任务可以离线完成、可以慢、可以反复重试、可以人工复核，不需要出现在推理的 critical path 上。

前提一旦不成立，"引擎必须内建算子生成"这条要求也就不再成立。

## 0.2 职责重新划分

把推理系统要做的事情按性质拆开，实际是三类：

| 职能 | 输入 | 输出 | 变化速度 | 归属 |
|---|---|---|---|---|
| 代码生成 | 语义图、融合决策 | kernel 实现 | 很快，随模型和硬件变化 | Agent 与离线 Kernel Harness |
| 运行时 | plan、KernelUnit、输入 buffer | 执行结果 | 很慢，十年尺度 | 引擎 |
| 正确性保证 | 契约、golden、容差 | 通过/失败与定位信息 | 慢 | 引擎 |

第一类工作的特点是需要创造，且没有确定性的算法可以替代。第二类和第三类工作的特点是可判定、可形式化、可测试。

这个划分就是项目的范围声明：中间和右边两列是引擎，左边一列不是。

### 为什么运行时与校验并不"薄"

常见的一个质疑是：不做图编译、不做算子生成，引擎不就是一个循环调用 kernel 的程序吗。

不是。即使限定在"只做运行时与校验"的范围内，一个可用的推理引擎仍然必须解决下面八个问题。这些问题都与模型语义无关、与具体硬件无关，也不会因为 Hopper 换代到下一代而失效：

1. 内存：生命周期分析、复用、别名合法性、对齐、workspace 切分、权重常驻、动态 shape 下的符号化偏移。
2. 并发：stream 与 event、跨流依赖、重叠执行、对显式并发声明的合法性校验。
3. 启动开销：整图捕获与重放、批量提交，把 N 次 launch 压缩成 1 次。
4. 动态性：形状符号绑定、variant 选择、覆盖域外降级、动态输出长度。
5. 正确性保证：逐 node 差分校验、容差约定、确定性检查、越界与对齐扰动测试、失败定位到 node/slot/index。
6. 可运维性：逐 node 耗时、显存水位、错误隔离、录制回放、超时检测。
7. 可移植性检查：特化指纹（fingerprint）的声明与校验，防止在 A100 上加载 H100 生成的包。
8. 供应链：Agent 生成的 kernel 属于不可信代码，需要沙箱、溯源、签名和审计。

这八件事都是横切关注点，必须由单一组件统一裁决。它们无法通过"让 Agent 顺手一起做"来解决，因为那样会让同一条约束存在多个实现，最终互相矛盾。

## 0.3 与操作系统的类比

把引擎理解成操作系统，比理解成编译器更贴近它的实际职责。编译器负责把一种语言翻译成另一种语言；操作系统不翻译任何东西，它定义 ABI、管理资源、加载程序、隔离故障、提供观测。

| 操作系统概念 | 本项目对应物 | 稳定性 |
|---|---|---|
| 可执行文件格式（ELF） | package（`.loom`） | S0 |
| 程序映像 | plan | S1 |
| 目标三元组 | fingerprint | S1 |
| 函数调用约定 | KernelUnit ABI | S0 |
| 虚拟内存与分配器 | arena 与符号化内存计划 | S0 |
| 进程 | session / invocation | S1 |
| 系统调用 | 引擎对外 API | S0 |
| 动态链接器 | 模块加载器（dlopen 与符号绑定） | S0 |
| perf、strace | 逐 node profiler、录制回放 | S1 |
| 编译器 | Agent 与 Kernel Harness（在引擎之外） | 自由演化 |

这个类比给出的最强约束是：操作系统从不需要理解你的程序在算什么，却能把资源管理得很清楚。推理引擎也应如此。

一个可执行的检验办法：如果引擎代码里出现 `if (op_type == "conv")` 这类分支，说明模型语义已经泄漏进引擎，设计被破坏了。

## 0.4 接口稳定性由抽象层次决定

接口能不能长期不变，取决于它所在抽象层次上硬件特性的变化速度。层次越高，变化越慢。

两个事实：

- `kernel<<<grid, block>>>(args...)` 这个调用形式从 CUDA 1.0（2007 年）沿用至今，形式没有变过。它只描述缓冲区、并行度和 stream，不涉及任何具体硬件机制。
- warp group、TMA descriptor、mbarrier、tcgen05、warp specialization 这些概念，平均两到三年更新一次。

TVM 的问题不在工程实现，而在于它把这些快速变化的概念写进了 IR 和 schedule 原语，也就是写进了本该稳定的那一层抽象。每次硬件换代都要重写，是必然结果。

### 推论一：ABI 只描述缓冲区

本项目的 ABI 只承认四种东西跨边界传递：缓冲区、标量参数、workspace 和 stream。

引擎不知道一个 kernel 内部用了几个 warp、是否使用 TMA、是不是 persistent kernel、有没有做 warp specialization。反过来，KernelUnit 内部可以任意复杂：可以是由多个 kernel 组成的流水线，可以是手写 PTX，可以是 cuTe 实例化产物，可以是 Triton 编译出的 cubin，也可以把整个 C2f 块融合成一个 persistent kernel。

接口本身很小，而 KernelUnit 内部没有限制。这一条同时解决两个问题：TVM 表达力不足的问题（不再需要表达，整块交给 kernel），以及可移植性问题（引擎不依赖内部结构）。

### 推论二：会被 Agent 重写的东西不能进入稳定层

判断一个元素该不该放进稳定层，标准不是它重要不重要，而是：如果它明天变了，引擎要不要改代码。要改，就不许进。

融合决策会变（硬件变了、Agent 变强了），必须在外部。kernel 实现会变（Triton 出新版本了），必须在外部。分块大小会变，连 plan 里都不应该写死，应放在 KernelUnit 内部或 variant 里。

## 0.5 引擎与模型语义的边界

这是整个架构唯一不可协商的约束：引擎理解数据流，不理解语义。它知道 slot A 被 node 7 写入、被 node 9 读取；它不知道那是一次卷积。

这条约束之所以重要，是因为它把"引擎会不会太笨"这个模糊质疑转成了一个可判定的问题：某项能力是否需要语义信息。

### 允许的能力（只需数据流信息）

| 能力 | 为什么不需要语义 |
|---|---|
| slot 生命周期分析 | 只看 node 的读写集合与顺序 |
| 内存复用与偏移校验 | 只看生命周期是否重叠 |
| 别名合法性检查 | 只看声明的读写集合 |
| 依赖图校验（无环、无悬空） | 只看边的连接关系 |
| 死 node 删除 | 只看输出是否被消费 |
| 形状符号求值 | 只看表达式与绑定表 |
| 并发编排（插入 event） | 只看声明的 stream 与依赖 |
| 逐 node golden 对比 | 只看字节与容差 |

### 禁止的能力（需要语义）

| 禁止项 | 原因 |
|---|---|
| 算子融合 | 需要知道两个 op 之间的数学关系 |
| 布局重排（如 NCHW 转 NHWC） | 需要知道每个 kernel 接受什么布局 |
| 代数化简（如 conv 与 bn 折叠） | 需要数学语义 |
| 算子选择与替换 | 需要知道哪些 op 等价 |
| 自动调度与自动分块 | 需要硬件模型与语义 |
| 识别 op 类型 | 一旦识别，就锁死在固定的 op 集合上 |

### 检验方法

把 plan 里所有 `ku` 名称替换为随机字符串，把所有 dtype 与 layout 标识替换为无意义编号，重跑全部测试。引擎应当仍然完整跑通、正确校验、正确报错。如果引擎在某处"猜"了语义，这个测试会立刻失败。这个测试应当作为独立的 CI job 常驻。

这条约束带来的一个额外好处是：引擎的规模可以停止增长。功能需求会不断出现，但只要不越过这条线，新增需求就只可能是资源管理类的，而这一类是有限的。

## 0.6 模型无关来自语义外置，硬件无关来自后端隔离

"稳定"不是形容词，它对应一份外置清单。凡是外置的部分，引擎都不再随它变化。

| 维度 | 外置给谁 | 外置产物 | 引擎看到什么 |
|---|---|---|---|
| 模型结构与算子语义 | Kernel Harness 与 Agent | plan 与 KernelUnit | 只有 slot 与 node 的连接关系 |
| 融合策略 | Agent | plan 的 node 划分 | 节点数量与粒度 |
| kernel 实现、分块、硬件机制 | Agent 与 DSL | `.so` 里的一个入口符号 | 一个函数指针与 caps |
| 数值容差 | 应用方的精度预算 | 契约字段 | 一个 rtol/atol 数值 |
| 硬件能力 | 后端适配层 | `LmDeviceCaps` | SM 数、smem、arch、带宽等标量 |
| 驱动与运行时差异 | 后端适配层 | 不透明的 stream 句柄 | 一个指针 |

需要特别说明的是硬件无关的实现方式。它不是"抽象出所有硬件的公共子集"——那是 TVM 的路线，在硬件快速演进时必然失败；而是"不抽象硬件，把硬件关在 KernelUnit 和后端内部"。

引擎对 CUDA 的全部认知只有：不透明的 stream 指针、`LmDeviceCaps` 里的十几个标量，以及 malloc/free/memcpy 几个函数。仅此而已。HIP、CPU、Metal 的差异也只体现在这十几个标量和几个函数指针上。

## 0.7 设计成立的前提与验证方法

一份设计文档应当说明自己在什么条件下成立。下面三条前提，每条配一个可以低成本执行的实验。

### 前提一：Agent 能在有限尝试内写出接近手写水平的 kernel

不确定之处：公开数据显示，在固定 shape 的单个算子上 Agent 可以接近甚至超过 PyTorch eager，但对上经过调优的库（cuBLAS、CUTLASS、TensorRT）普遍低于 1 倍，且在复杂融合算子上退化明显、方差很大。

验证方法：取 YOLOv8n 中最难的三个融合单元，在固定预算（不超过 20 次尝试）内让 Agent 实现，与手工实现对比。

失效条件：三个单元中有两个无法达到手写版本的 70%。此时"Agent 替代算子生成"这一前提在本项目的时间尺度内不成立。

需要注意，这个前提失效并不意味着项目必须放弃，原因见本节末尾。

### 前提二：特化的经济性成立

不确定之处：每个（模型，硬件，shape 类别）组合都是一次性工程投入。TensorRT 用自动融合与自动选 kernel 把边际成本压到接近零；本项目把边际成本换成了 Agent 工时、GPU 工时与调试时间。

验证方法：完整记录一次 YOLOv8n 特化的真实成本（人时、token、GPU 小时、调试时间），与直接用 TensorRT 部署的成本对比。

失效条件：边际成本超过 TensorRT 方案的 3 倍。此时目标场景必须收窄到高频、高价值、长期维护的少数部署。

### 前提三：契约稳定性带来的收益大于放弃自动优化的损失

不确定之处：自动融合在未知模型上通常能带来 20% 到 40% 的性能提升；交给 Agent 之后可能漏掉融合机会。

验证方法：同一模型分别用（a）Agent 决策的融合加本项目引擎，（b）TensorRT，比较端到端延迟，并统计（a）中漏掉融合机会的比例。

失效条件：（a）稳定慢于 TensorRT 15% 以上，且差距主要来自融合决策而非 kernel 质量。此时应在 Kernel Harness 中补充一个确定性的规则融合提议器（不在引擎中），把 Agent 的职责收窄到 kernel 实现。

### 关于前提失效的处理

上面三条前提都在赌 Agent 的能力曲线。但项目的核心资产不是 Agent，而是契约本身：

- 如果 Agent 变强，契约照常使用，产物质量提高。
- 如果 Agent 进展停滞，人类专家仍然可以按契约产出 KernelUnit，引擎照常工作。
- 如果将来某个编译器真正解决了合成问题，它只是另一个生产者，把输出包装成 KernelUnit 即可。

引擎对"谁生产了 kernel"保持无知，这是它能够长期存在的原因。前提取决于外部因素，契约只取决于我们自己。

## 0.8 不做的范围

明确列出不做的部分，比列出要做的部分更能防止项目范围扩散。

| 不做 | 原因 |
|---|---|
| LLM 推理（KV cache、continuous batching、PD 分离） | 需求形态不同：LLM 的瓶颈是调度与状态管理，不是算子。留作后续课题，架构上预留 request 级并发 |
| 训练、反向传播、自动微分 | 与推理的稳定性需求冲突 |
| 分布式与多机 | 先把单机单卡多流做好 |
| 自动并行与自动分片 | 需要语义 |
| 图编译优化（任何 pass） | 见 0.5 节 |
| 引擎内的算子生成 | 见 0.2 节 |
| 前端格式全覆盖 | 第一版只支持 ONNX 与 TorchScript，其他通过 Kernel Harness 转换 |
| 多厂商插件生态 | 先做一个半后端（CUDA 完整，CPU 作参考） |

关于 LLM 的边界说明：本设计不排斥 LLM。将来若要支持，正确的做法是在本引擎之上加一层请求调度器（batch 组装、KV 管理），把一次 forward 做成一个 plan，把 KV cache 做成 persistent slot。这同时也是一次检验：如果支持 LLM 不需要改动引擎内部，说明 0.5 节的边界划得是对的。

## 0.9 结论

这个项目要做的不是"会写程序的引擎"，而是"任何程序都能正确、可诊断地跑起来"的引擎，并假定这些程序由 Agent 写出来。

由此得到的定位是：一个面向 Agent 产物的推理运行时。它负责加载、执行编排、校验与诊断；不负责翻译、不负责优化、不负责生成。

需要说明的是，这个定位并不能让项目变简单。它只是把复杂度从"引擎内部的编译优化"转移到了"契约、Kernel Harness 与验收流程"。`12-risks.md` 会详细讨论这个转移带来的代价，其中成本模型是最大的风险。
