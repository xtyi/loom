# 15 待讨论问题与待定决策

本文记录两类未定事项。

第一类需要发起人判断，涉及定位、范围与资源投入，技术上没有对错，但选错会让后面所有工作失去方向。

第二类是可以自己判断的技术决策，有明确选项和倾向，但必须在一个固定时间点之前定下来，否则会阻塞实现。

---

## 1 需要先讨论的问题

### Q1 项目名称

已定为 Loom，字面意思是织机：经线是固定的接口与编排，纬线是 Agent 产出的 kernel，引擎负责把两者织成可运行的程序。

连带确定的命名规则：

| 对象 | 规则 | 示例 |
|---|---|---|
| 运行时 | `loom-rt` | `loom-rt` 头文件在 `include/loom/` |
| Kernel Harness | `loom-harness`，Python 包名 `loom_harness` | `loom-harness gen --group 17` |
| 命令行 | `loom-cli` | `loom-cli run --pkg model.loom` |
| C ABI 类型 | 前缀 `Lm` | `LmBuffer`、`LmKernelArgs` |
| C ABI 函数与宏 | 前缀 `lm_`、`LM_` | `lm_session_run`、`LM_E_ABI` |
| 包扩展名 | `.loom` | `yolov8n-h100.loom` |
| 包格式标识 | `loom/1.0` | `"format": "loom/1.0"` |

备选过但未采用的名称：Tenon（榫）、Vouch（担保）、Keel（龙骨）、Gantry（龙门架）、Assay（验金）、Rivet（铆钉）、Baton（指挥棒）、Kiln（窑）。记录在这里是为了将来若需要子项目或工具名时可以参考。

需要注意 Loom 这个名字已被若干产品使用，包括 Meta 的并发调试工具和一款录屏工具。内部使用没有影响，对外商用前需要检索商标与域名。

### Q2 使用者是谁

这决定 Kernel Harness 做到什么程度才够用。

三种可能。第一种是 kernel 工程师，他们自己会写 CUDA，Agent 只是加速器；此时 Harness 的自动化可以很低，人工介入是常态。第二种是算法工程师，他们能改模型但不会写 kernel；此时 Harness 必须把校验、重试、调优全部包起来，并且失败时能给出人能看懂的解释。第三种是平台团队，他们不碰模型，只负责把一个已经调好的包部署到几百台机器上；此时 Harness 可以很粗糙，但包格式和运行时必须可靠。

三种用户的优先级不同，模块投入比例差很多。

### Q3 成功标准

性能领先 TensorRT 10% 和"部署周期从月降到天"，是两种完全不同的项目。

如果是前者，重心在融合策略与 kernel 质量，投入集中在 M2 到 M3。如果是后者，重心在工具链易用性与稳定性，即使每个 kernel 只达到手写版本的 85% 也可以接受。

需要明确一个可验收的说法，否则 10 文档第 6 节的门槛无法设定。

### Q4 是否接受"每个模型一次性工程"

这是整个构想最根本的商业问题，12 文档把它列为唯一最高优先级风险。

如果目标场景里模型数量多、每个模型只部署一两次，那么按模型特化的成本无法摊销，这个方向不成立。

如果目标场景是少数模型长期运行，或者模型频繁出新但硬件固定，成本可以摊薄。

这一条不问清楚，后面所有关于复用的设计都是在猜。

### Q5 模型与权重的交付形式

我们假设能拿到 ONNX 或 TorchScript。现实中常见三种情况：客户给原始模型；客户只给加密后的包；客户给的是已经转换过的中间格式。

第二种情况下 Kernel Harness 无法做语义分析，整个方案不成立，只能退回"运行时加手写 kernel"。这一点需要在接触客户前确认。

### Q6 硬件范围

第一版是否只做 NVIDIA 数据中心卡，还是必须覆盖 Orin、Jetson 这类边缘设备，或者还要考虑国产加速卡。

范围直接决定后端工作量与指纹设计的复杂度。多一个后端，M3 之后至少多四到六周。

### Q7 精度路径

FP16 是主线。INT8 与 FP8 什么时候进入，由谁决定量化参数，校验怎么做，目前都没有答案。

量化会引入 scale 传播，这项工作在 Kernel Harness 里，属于独立的一大块。如果客户第一版就要求 INT8，M4 的排期要重做。

### Q8 厂商库的许可

cuDNN 不允许再分发。如果包依赖 cuDNN，等于要求客户环境里已经装好匹配版本的 cuDNN，这会给部署带来额外约束。

需要决定：是把厂商库作为可选加速（缺失时降级到自写实现），还是作为必需依赖。前者更稳妥，但需要每个关键算子都有自写版本。

### Q9 团队能力

M1 阶段要手写三十个 kernel，其中 C2f、SPPF 这类融合块需要读懂 Hopper 的 TMA 与 warp specialization。如果团队里没有人能做到，M1 的时间估计要翻倍，或者需要先用 Triton 做出可以接受的版本。

另外，人工评审 Agent 产出的 kernel 需要有人看得懂，这是 G2 门禁的前提。

### Q10 开源与知识产权

引擎与 Kernel Harness 是否开源，开源哪一半，用什么许可证。

另外，Agent 生成的代码归属如何界定，是否需要把许可扫描作为强制门禁。这一点在 01 文档 P12 里已经写成要求，但具体执行标准还没定。

## 2 需要做的技术决策

下表是可以在内部判断的决策。倾向一列是当前看法，不是最终结论。

| 编号 | 决策 | 选项 | 倾向 | 截止 |
|---|---|---|---|---|
| D1 | CPU 后端的定位 | 仅参考实现；生产可用 | 参考实现，只用于无 GPU 的 CI | M0 |
| D2 | 一个实现一个 `.so` | 保持；改为按 KernelUnit 合并 | 保持，见决策 0002 | M0 |
| D3 | plan 是否引入二进制格式 | 只用 JSON；增加二进制 | 只用 JSON，第一版体积不是问题 | M1 |
| D4 | 是否支持动态控制流 | 不支持，用固定容量绕开；支持 if 与 loop | 不支持，先覆盖检测类模型 | M1 |
| D5 | CUDA Graph 的默认策略 | 默认开；默认关，显式开启 | 默认开，profile 时自动关闭并提示 | M1 |
| D6 | 内存计划的默认模式 | auto；explicit | auto，性能敏感时由 Kernel Harness 产出 explicit | M2 |
| D7 | 校验在 CI 的默认档位 | 只跑 L1；L1 加 L2 | L1 每次提交，L2 每晚 | M1 |
| D8 | 归因是否集成 NCU | 只导出可复现命令；直接调用 ncu | 只导出命令，避免依赖 ncu 的可获取性 | M2 |
| D9 | 是否允许运行期生成 kernel | 禁止；允许按首次请求触发 Agent | 禁止，生成是构建步骤 | 已定，见 P14 |
| D10 | SemanticGraph 的覆盖范围 | 只覆盖 CNN 与检测；覆盖 attention block | 先覆盖前者，M4 引入 RT-DETR 时扩展 | M4 |
| D11 | 签名与密钥管理 | 自建 registry 签发；先用本地签名 | 本地签名，M3 再接 registry | M3 |
| D12 | 是否对外发布包格式标准 | 只内部使用；作为标准发布 | 内部使用，等 M4 数据出来再定 | M5 |
| D13 | 多 session 共享权重的粒度 | 每个 session 独立 arena，权重共享 | 共享权重，arena 按 session 独立 | M2 |
| D14 | workspace 复用是否需要在 plan 中声明 | 引擎自动复用；plan 显式声明 | 引擎自动，显式声明留给 explicit 模式 | M2 |

下面四项影响面较大，单独说明。

### D1 CPU 后端的定位

如果 CPU 后端只是参考实现，它只需要正确、不需要快，M0 的工作量可控，而且能让无 GPU 的 CI 跑全部逻辑测试。

如果要求生产可用，需要处理线程池、NUMA、SIMD 分派，工作量至少翻倍，而且是另一个领域的能力。

倾向是前者。生产场景里的 CPU 推理有 ONNX Runtime 这类成熟方案，没有必要重复。

### D4 动态控制流

当前设计用"固定容量加计数"表达 NMS 这类长度可变的输出，绕开了控制流。这对检测类模型够用。

但有些模型包含真正的数据相关分支，例如自适应计算、早退网络或多阶段级联。这种模型需要 plan 支持条件节点，而 CUDA Graph 对条件节点的支持从 12.4 才开始，代价也要重新评估。

倾向是第一版不支持，把这类模型明确列为不适用范围。如果客户场景确实需要，再单独立项。

### D5 Graph 的默认策略

默认开启的收益是小 batch 下省 5% 到 8%，代价是第一次运行多一次捕获、显存占用略增、profile 时行为不同。

关闭的好处是行为简单、可预测，坏处是用户很可能不知道这个开关存在。

倾向是默认开启，但在 profile 时自动关闭并打印提示，避免出现"profile 结果与线上不一致"的困惑。

### D10 SemanticGraph 的覆盖范围

如果只覆盖 CNN 与检测，M1 到 M3 的路径较短，但 M4 引入 RT-DETR 时需要扩展语义图，可能要改融合分组和布局传播的部分逻辑。

如果一开始就覆盖 attention，前期工作量增加，但后续模型接入更顺。

倾向是先窄后宽。理由是 M1 到 M3 的目标是验证机制，不是覆盖模型种类。

## 4 建议的讨论顺序

Q4 决定项目是否值得做，应当最先回答。如果答案是"模型多且部署次数少"，那么后面的技术问题都不必讨论。

其次是 Q2 与 Q3，它们决定 Kernel Harness 的投入比例和验收标准。

Q5、Q6、Q7 决定范围，可以在验证期结束前定。

Q8 到 Q10 属于执行层面的风险，进入 M0 之前定即可。

技术决策里只有 D1 和 D2 阻塞 M0，其余都可以边做边定。
