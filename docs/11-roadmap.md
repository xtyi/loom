# 11 计划

计划的第一条原则是先验证再实现。这个构想的核心假设是"Agent 能接管 kernel 生产"，如果不先验证，就会在错误的假设上投入半年。

---

## 1 阶段总览

| 阶段 | 周期 | 主要目标 |
|---|---|---|
| M-1 验证期 | 3 到 4 周 | 判断三个核心假设是否成立，决定是否开始 |
| M0 接口与骨架 | 4 到 5 周 | 冻结 ABI，用 CPU 后端证明 plan 执行模型正确 |
| M1 CUDA 与手写 | 6 到 8 周 | YOLOv8n 端到端跑通，全部 kernel 由人工编写 |
| M2 Kernel Harness 与单点验证 | 6 周 | 用 Agent 替换三个难组，验证产出质量 |
| M3 全量与产品化 | 6 到 8 周 | 全部由 Agent 产出，补指纹、签名、第二硬件 |
| M4 复用性验证 | 8 周 | 第二个模型、INT8、生产加固 |
| M5 定位选择 | — | 根据前面数据决定开源、商业化或转为内部工具 |

总计约 9 到 12 个月，两到三名工程师。验证期的三到四周不能省，它决定了后面半年是否值得投入。

---

## 2 M-1 验证期（3 到 4 周）

目的不是做出东西，而是用最低成本判断这条路通不通。

### E1：语义无关的引擎是否够用（2 周，最高优先级）

做法：

1. 手写三个 YOLO 融合 kernel（conv-bn-silu、C2f、sppf），用 Triton 或 CUDA。
2. 写一个最小执行器，约 800 行，只按声明的 slot 生命周期分配，只按声明顺序 launch，不理解任何算子语义。
3. 与 TensorRT fp16 对比端到端耗时与峰值显存。

要回答的问题是：为了让执行器正确工作，需要 Agent 回传多少语义信息。

判定：

- 通过：声明负担不超过每个 kernel 十个字段，且显存规划与 TensorRT 的差距在 15% 以内。
- 不通过：必须把逐 tensor 的生命周期、别名和布局作为自由文本回传，或显存差距超过 30%。
- 不通过时的动作：改写为带融合感知的 plan IR，即承认引擎需要一部分语义。这仍然是个项目，但不是本文档描述的这个。

这个实验检验的正是 00 文档 0.5 节的边界能否守住。

### E2：Agent 能写到什么水平（3 周，与 E1 部分并行）

做法：取五个最耗时的算子（3×3 s2 卷积、1×1 卷积、concat、upsample 加 sigmoid、C2f 融合块），让 Agent 迭代不超过 20 轮，并给出完整校验反馈。

要回答的是相对 cuDNN 与 CUTLASS 的几何平均性能、首次可用时间、人工介入次数。

判定：

- 融合块 C2f 达到手写版本的 90%，核心假设成立。
- 孤立卷积只有 0.5 到 0.9 倍，这在预期之内，由厂商库优先策略吸收，不构成否决。
- 融合块也低于 70%，说明"Agent 接管 kernel 生产"不成立，退化为"Agent 做选择，人写 kernel"。引擎本身仍然有价值。

### E3：需求是否存在（2 周，可与技术实验并行）

做法：访谈八个实际部署检测或 CNN 模型的团队，问现用技术栈、端到端延迟构成、迁移成本，以及是否愿意为"快 20%"或"可审计可复现"更换技术栈。

判定：如果超过七成已经在用 TensorRT，且认为理论空间小于 1.3 倍，性能叙事作废，必须转向可维护性与多硬件叙事，或者放弃商业化，只做内部工具与开源。

### E4：成本模型（贯穿 M0 到 M3）

记录每个模型与硬件组合的真实成本：人时、token、GPU 小时、重试率。E4 没有终点，它是项目的仪表盘。

### 决策会议

四周结束时开一次会，只回答一个问题：继续、改写还是放弃。三个选项都必须是真实可选项，否则会议没有意义。

## 3 M0 接口与骨架（4 到 5 周）

目标是把 ABI 冻结，并用 CPU 后端证明 plan 的执行模型是对的。

| 交付物 | 验收 |
|---|---|
| `include/loom/ku_abi.h` 与 `rt.h` | 通过一次外部评审，之后冻结 |
| `plan/`：JSON 解析、`SymExpr` 求值、谓词、variant 选择 | 单元测试覆盖率 100%，这是纯逻辑 |
| `mem/`：arena、liveness 分配、别名校验 | 对二十个手工构造的 plan 验证通过与拒绝 |
| `exec/`：依赖图、提交、CPU 后端 | 多线程 CPU 后端跑通 |
| `conform/`：L0 与 L1 | 能报出 node、slot、索引 |
| `loom-cli run`、`validate`、`inspect` | 端到端可用 |
| ABI 语料 CI | 至少一个包常驻，每次 CI 加载 |
| 语义无关性测试 CI | plan 全部改名后行为不变 |

M0 的门禁最严：`ku_abi.h` 冻结。冻结之后任何改动都需要决策记录和兼容性分析。

先做 CPU 后端的原因是，它让你在没有 GPU 的 CI 上跑全部逻辑测试。GPU runner 昂贵且可获取性差，这个决定能把 CI 成本降低一个数量级。

---

## 4 M1 CUDA 后端与手写 YOLO（6 到 8 周）

这一步是整个计划里最重要的，也是最容易被跳过的。

| 交付物 | 验收 |
|---|---|
| CUDA 后端，含 arena、stream、event、graph、caps | 与 CPU 后端行为一致，使用同一批测试 |
| 30 到 35 个手写 KernelUnit | 每个都有 ref 与 fast，都有 L1 golden |
| Kernel Harness 的 `ingest`、`refrun`、`emit` 最小版本 | 能从 ONNX 产出可运行的 plan |
| profiler 与归因 | 能报出逐 node 耗时与瓶颈分类 |
| 基准脚本与三方对照 | TensorRT、ONNX Runtime、本项目，固定协议 |

门禁：

- 不慢于 ONNX Runtime CUDA fp16，即第一档。
- mAP 下降不超过 0.3。
- 引擎开销不超过 5%，即 `lm_kernel_time_fraction` 不低于 95%。

必须先手写的原因：如果跳过这一步，M2 会同时变化两个未知数，任何失败都无法归因。手写版本是后续所有实验的对照组，也是 Agent 的样例来源。

风险是六到八周写三十个 kernel 时间偏紧。应对方式：

- 从 CUTLASS 与 Triton 的官方样例改写，不从零开始。
- 先写符号化版本，正确即可，性能留到 M3。
- 复用厂商库：孤立卷积直接用 cuDNN，只手写八到十个融合块。

最后一条把 M1 的工作量从三十个降到十个，这是厂商库优先在计划层的直接收益。

## 5 M2 Kernel Harness 与单点验证（6 周）

| 交付物 | 验收 |
|---|---|
| `gen` 脚手架与 shim 模板，覆盖 TileLang 与 CUDA | Agent 拿到脚手架即可开始 |
| 闭环状态机与修复建议表，见 07 文档第 6 节 | 能自动重试并收敛 |
| 三个难组（g11 C2f、g19 SPPF、g24 detect head）由 Agent 实现 | 达到手写版本的 90% |
| 单组成本测量 | 不超过 4 小时实际耗时，不超过 30 GPU 分钟 |
| 审计 Agent 与人类门禁 G1、G2 | 至少完整走一轮 |

门禁：

- 三个组中至少两个达到 90%，这是项目的成败线。
- 失败率低于 60%，即一半以上的组能在预算内成功。

门禁失败时不要立刻放弃，先做归因：是反馈质量不够，应当改进报告；还是任务切分太大，应当拆小；还是模型能力不足，应当换模型或加检索。这三种原因的处理方式完全不同。

## 6 M3 全量与产品化（6 到 8 周）

| 交付物 | 验收 |
|---|---|
| 全部组由 Agent 产出 | 整体达到手写版本的 95% |
| 调优 | 相对默认参数再提升 5% 以上 |
| 包格式、指纹、签名、溯源 | 跨 arch 加载用例：正确拒绝与正确接受 |
| 本地版 registry | 能按模型与指纹检索并复用 |
| 第二个硬件目标，例如 sm86 或 Orin | 同一套流程产出可运行的包 |
| 生产加固，含沙箱、超时、上下文失效隔离 | 故障注入测试通过 |

门禁：

- 从新硬件到可运行的包不超过三天，这是本项目最重要的产品指标。
- INT8 不在此阶段，留到 M4。

---

## 7 M4 复用性验证（8 周）

目的是回答"按组合计算的成本是否可控"。

| 交付物 | 验收 |
|---|---|
| 第二个模型，例如 RT-DETR 或 ResNet-50 | 从零到可部署不超过两周，对比第一个模型的六个月 |
| KernelUnit 复用率测量 | 不低于 50% 的 KernelUnit 直接复用而不重新生成 |
| INT8 量化路径 | scale 传播由 Kernel Harness 处理，容差单独标定 |
| 三个模型乘两个硬件的成本矩阵 | 数据支撑后续商业判断 |

选择 RT-DETR 是因为它引入 attention，可以验证架构不只对 CNN 有效，又不需要触及 LLM 的复杂度。

如果复用率低于 30%，说明"每个模型重新生成"的成本无法摊销，必须转向可组合的 KernelUnit 库加模板路线，或者把目标收窄到少数长期维护的模型。

## 8 M5 定位选择

这不是工程阶段，取决于 M4 的数据。三条路：

| 路线 | 条件 | 形态 |
|---|---|---|
| A 开源基础设施 | 复用率高，社区有需求 | 引擎与 Kernel Harness 开源，靠托管服务或支持变现 |
| B 垂直产品 | 找到高价值场景，例如边缘多路视频或受监管行业 | 打包成行业方案 |
| C 内部工具或副产品 | 成本模型不成立 | 抽出"接口约定加校验"做 kernel CI，见第 9 节 |

---

## 9 降级预案

这不是失败主义。三条前提任何一条不成立时，项目应当保留什么价值，需要提前想清楚。

| 若不成立 | 保留什么 | 变成什么 |
|---|---|---|
| Agent 写不出好 kernel | 引擎、ABI、校验 | 人工 kernel 团队加稳定运行时，对新模型仍比 TensorRT 灵活 |
| 接口约定无法覆盖语义（E1 失败） | 校验与 Kernel Harness | 带融合感知的离线编译器，半个编译器，但比 TVM 务实 |
| 商业上不成立 | 校验与门禁工具 | kernel CI：正确性、性能与回归门禁，这个方向确实缺，且不需要打败 cuDNN |
| 成本模型不成立 | 接口约定与包格式 | 模型包标准，让别人按这个格式交付，我们做加载器与校验器 |

四条降级路径共享同一个资产，就是接口约定。这也是 01 文档 P4 与 P11 值得在项目一开始就投入的原因。

## 10 人员与预算

| 角色 | 人数 | 关键能力 |
|---|---|---|
| 运行时与系统 | 1 | C++、CUDA 内存与流、多线程、ABI 设计 |
| GPU kernel | 1 | CUDA、Triton、TileLang，会看 NCU，了解 Hopper |
| Kernel Harness | 0.5 到 1 | Python、图变换、布局传播 |
| 算法与产品 | 0.5 | ONNX、模型量化、与客户沟通 |

Agent 预算按 token 计约每月 2000 到 8000 美元，GPU 机时另计。相对人力成本这不是主要开销，主要开销是人的时间。

## 11 门禁汇总

| 阶段 | 门禁 | 不通过的动作 |
|---|---|---|
| M-1 | E1 通过，且 E2 中融合块不低于 70% | 改写架构，或降级为第 9 节的方案 |
| M0 | ABI 冻结，语义无关性测试与语料 CI 通过 | 不冻结不许进入 M1 |
| M1 | 不慢于 ONNX Runtime，mAP 达标，引擎开销不超过 5% | 回到 M0 修执行器 |
| M2 | 三分之二的难组达到 90%，失败率低于 60% | 归因后决定：改反馈、拆任务或换模型 |
| M3 | 新硬件到包不超过三天，跨 arch 拒绝正确 | 补 Kernel Harness，不进入产品化 |
| M4 | 第二模型不超过两周，复用率不低于 50% | 转第 9 节的方案 C |

每个门禁都必须写明不通过时怎么办，否则门禁只是仪式。
