# 01 设计原则

原则的作用是在具体分歧上给出裁决依据，而不是表达愿景。每条原则包含三段：内容、必要的理由、以及可执行的检查方式。

编号固定为 `P<n>`，设计评审、代码评审和决策记录都引用编号。如果某条原则需要被打破，必须写一份决策记录说明理由，并同步修改本文。

---

## P1 引擎不参与数值计算

推理执行核心不参与张量数值计算，所有模型计算（含 Cast、量化与反量化）发生在 KernelUnit 内。按需启用的校验服务可以计算误差指标，但不能改变推理结果。引擎只决定何时、在哪个 stream、用哪块内存、调用哪个入口。

理由是：一旦引擎拥有哪怕一个内建快速路径算子，就会出现针对特定 op 的分支，P2 随即失效。

检查：`runtime/` 下不得引用 cutlass、cublas、cudnn；除 memcpy/memset 和独立 conform 校验模块外，不得有模型数值计算代码。CI 用 grep 白名单检查。

---

## P2 引擎不依赖模型语义

引擎理解数据流，不理解计算内容。它知道某个 slot 被哪个 node 写入、被哪个 node 读取，不知道这些 node 在算什么。

检查：一致重命名 `ku` 及其注册项、重映射不透明 layout 标签后，行为必须不变。dtype 保留已定义的编码和存储语义，用于大小计算与类型校验；未知 dtype 必须拒绝。

---

## P3 跨边界信息必须显式声明

dtype、shape、stride、别名关系、读写集合、workspace 大小、对齐要求、确定性、容差，全部由生产者声明，并写入可校验的结构化字段。引擎不得从其他信息推断这些内容。

理由是：推断需要语义，声明可以被校验。声明错了引擎能报错；推断错了引擎会静默算错。

检查：对每个可选字段回答一个问题——字段缺失时引擎会做什么。答案必须是"报错"或"使用文档化的保守默认值"，不能是"猜"。

---

## P4 每个接口元素标注稳定性等级

仓库中出现的每一个跨边界结构体、枚举、文件格式、函数签名和 CLI 参数，都要标注等级：

| 级别 | 含义 | 变更规则 |
|---|---|---|
| S0 | 冻结 | 只能末尾追加字段（配 `struct_size`）、追加枚举值、新增符号 |
| S1 | 稳定 | 语义不变，允许向后兼容的扩展；破坏性变更需 major 版本和迁移工具 |
| S2 | 实验性 | 可随时修改，需显式开关启用 |
| S3 | 内部 | 不承诺 |

当前处于原型期，文档中的 S0/S1 是发布后的目标等级，尚未生效；冻结条件见 03 文档第 0 节。

等级的判定依据是 00 文档 0.4 节：如果该结构在未来两年内可能需要改字段而不只是加字段，就不能是 S0。

检查：`03-contracts.md` 的主表必须与头文件注释一一对应，CI 用脚本比对。任何新增公共符号没有标注等级的 PR 视为未完成。

---

## P5 编排由确定性程序生成，kernel 实现由 Agent 生成

plan 的 node 划分、slot 分配、连线、内存偏移、stride 由确定性合成器生成，不由 LLM 生成。LLM 的自由度限制在两类产物：融合分组建议，以及单个 KernelUnit 的实现。

分工如下：

| 产物 | 生产者 | 可否用 LLM | 校验方式 |
|---|---|---|---|
| 语义图解析 | Kernel Harness | 否 | 与参考实现逐 node 对齐 |
| 融合分组 | Agent | 是 | 结构合法性检查加实测性能 |
| plan 连线、slot、偏移 | Kernel Harness 合成器 | 否 | 引擎校验器与生命周期检查 |
| kernel 源码 | Agent | 是 | 编译、差分校验、扰动测试 |
| kernel 参数 | Agent 或调优器 | 是 | 实测 |
| 容差 | 应用方配置 | 否 | 领域指标（如 mAP） |
| 布局与 stride | Kernel Harness | 否 | 校验器 |

理由是：plan 的连线是一组机械变换，不需要创造力，但出错是静默的——连线错了不会报错，只会算错。kernel 实现则相反，它有客观判据（跑得对、跑得快）。

检查：Kernel Harness 的 `emit/` 模块不得 import 任何 LLM 客户端库，CI 检查 import 图。

---

## P6 每个 KernelUnit 必须有参考实现和降级路径

每个 KernelUnit 都要提供 ref 实现（朴素但正确）和至少一个 fast 实现。任何时刻只要 plan 通过校验，就一定存在一条能跑出正确结果的路径。

降级顺序为：tuned 实现 → 默认参数实现 → 其他 arch 的实现 → ref 实现 → 拒绝并给出结构化诊断。

理由有三个：没有 ref 就没有差分校验的 oracle；没有 ref 就没有线上兜底；ref 同时也是 Agent 的起点，符合先写对再写快的迭代节奏。

检查：任何 KernelUnit 缺少 ref 时 `pack` 命令必须失败。降级必须产生可观测事件，不允许静默降级。

---

## P7 错误必须定位到 node、slot 和索引

引擎报告的任何错误都要定位到最小可行动单元：哪个 node、哪个 slot、什么 shape、第几个元素、期望值与实际值。

理由是：这是 Agent 闭环唯一的反馈来源。Agent 无法从 "illegal memory access" 学到任何东西，但可以从"node 17 的 out[0] 在 index (3,71,118,42) 处 abs_err=0.031，超过容差 0.002，且该索引对应输入 slot 5 的 padding 区域"中学到很多。

检查：所有人为构造的失败用例，报错信息必须包含 `node_id`。

---

## P8 执行依赖与调度分离

plan 的 DAG 定义数据依赖与额外的 `after` 边；schedule 可指定合法的提交顺序与 stream 分配。没有 schedule 时使用确定性拓扑排序，就绪节点按 id 升序取出，默认全部提交到 stream 0。

依赖调度不需要算子语义，前提是读写、别名和副作用声明完整。节点 id 仅用于标识和就绪集合的稳定选择，不能替代依赖关系。高级并发启发式可以以后增加，第一版不实现自动多流调度。

检查：依赖环、悬空引用、缺失生产者必须拒绝；显式提交顺序必须覆盖全部节点且满足所有依赖。多流内存复用必须由完成关系证明安全，不能把 CPU 提交顺序当成设备完成顺序。

---

## P9 硬件特化必须声明并在加载时检查

任何针对特定硬件的假设（arch、smem 容量、TMA 可用性、驱动版本、dtype 支持）都写入 package 的 requires 字段，并在加载时校验。不匹配时默认拒绝加载，除非显式指定 `allow_unvalidated`。

理由是：编译器生成的 kernel 在运行时自己会做 dispatch，而 Agent 生成的 kernel 可能直接硬编码指令集。如果静默跑在不适配的硬件上，结果是非法指令或静默错误。

检查：fast 实现缺少 `min_arch` 声明时 `pack` 失败。arch 比较必须使用（family, feature_set）二元组，禁止用整数大小比较，因为 `sm_90a` 与 `sm_90` 互不兼容。

---

## P10 性能结论必须附测量

任何"更快"的说法必须附带测量方法、测量环境和可复现的命令。引擎的职责是暴露数据（逐 node 耗时、带宽、显存水位、launch 次数），而不是猜测优化机会。

理由是：在引擎不做优化的架构下，性能责任外移到了 Agent。如果引擎不提供高质量数据，Agent 就是盲飞。

检查：instrumentation 提供 off / node / full 三档，默认 off 的开销接近零。基准测试固定 warmup 次数、迭代次数与锁频设置。报告必须同时给出引擎自身开销与端到端耗时。

---

## P11 运行时保持精简，接口约定完整

"精简"指引擎的代码量和可变部分；契约（ABI、格式、校验规则、诊断质量）必须完整。判断标准可以粗略看作契约覆盖的失败模式数量与引擎代码行数之比。

这是对"不做融合不做代码生成，引擎还剩下什么"的正面回答。引擎的薄是设计结果，不是偷懒结果：复杂度被转移到了契约与 Kernel Harness 上，而契约是一次性投入、长期复利。

检查：某个功能如果能通过增加一条校验规则实现，就优先加校验，而不是增加执行逻辑。

---

## P12 Agent 产物按不可信输入处理

Agent 生成的 kernel 源码、编译产物、plan 和参数，一律按供应链不可信输入处理，具体要求：

1. 沙箱：编译与首次运行在受限环境（无网络、限内存、限时、只读挂载）。
2. 溯源：每个产物携带 provenance（agent 版本、模型 id、prompt hash、工具版本、seed、评审人）。
3. 签名：package 必须签名，引擎校验签名者白名单。
4. 源码保留：包内必须保留 kernel 源码，不能只存 cubin，否则无法审计、无法复现、无法在硬件换代后重编译。
5. 许可扫描：Agent 可能从 CUTLASS 等来源记忆出代码，`pack` 阶段必须做许可证扫描。

检查：prod 档位下加载无签名的包必须失败。许可扫描不通过的包不允许打包。

---

## P13 同一 KernelUnit 的多个实现共享同一份声明

ref、fast、tuned 三个实现共享同一份 manifest、同一套参数 schema、同一个 io 声明，差异只在实现代码与调优参数。

理由是：否则会出现 ref 与 fast 的参数语义不一致，差分校验因此失效。这是最隐蔽的一类 bug。

检查：manifest 一致性校验器检查同一 KernelUnit 下所有实现的 params schema 与 io 声明完全一致。

---

## P14 编译与代码生成全部离线完成

运行时只做加载、校验、分配、提交、同步和观测。运行时依赖中不得出现 Python、LLVM、TVM、ONNX、torch 或任何编译器前端。

例外是形状符号求值与 variant 选择，它们必须在运行时进行，但只限于对已编译表达式求值，不做任何代码生成。

理由是：这决定了引擎能进入哪些环境（车载、嵌入式、边缘设备，以及不接受 Python 的企业场景）。这也是 TensorRT 长期以来的优势：一个纯 C++ runtime 加一个序列化的 plan 文件。

检查：`ldd` 输出必须在白名单内，即系统库加 CUDA/HIP 运行时。

---

## P15 需要语义的优化放在 Kernel Harness，不放运行时

所有需要理解模型语义的优化——融合分组、布局传播与重排、算子选择、精度选择、量化策略与 scale 传播——都在 Kernel Harness 完成。基于已声明数据依赖的 buffer 复用和拓扑调度可由运行时实现；昂贵的搜索与调优优先离线。Kernel Harness 可以做完整的语义分析，可以任意复杂，可以依赖 PyTorch 与 ONNX。

引擎只接收这些决策的结果（plan 中的 slot 布局、node 划分、内存偏移），并验证其合法性。

这条原则是对一个有力质疑的回应："引擎不懂语义就做不了全局优化，端到端必然输给 TensorRT。"这个质疑成立的前提是"优化必须在运行时发生"。但在本架构下，优化并不发生在运行时：

| 优化 | 传统引擎的执行位置 | 本项目的执行位置 | 引擎需要语义吗 |
|---|---|---|---|
| 算子融合 | 运行时图 pass | Kernel Harness 生成 plan 时 | 不需要 |
| 布局传播 | 运行时图 pass | Kernel Harness 生成 plan 时 | 不需要 |
| buffer 全局复用 | 运行时 allocator | Kernel Harness 的显式内存计划 | 不需要 |
| 算子选择 | 运行时 tactic 选择 | Kernel Harness 与 Agent | 不需要 |
| 形状特化 | 运行时 JIT 或 tactic | Kernel Harness 的 variant | 不需要 |
| 多流重叠 | 运行时自动 | 初期由 schedule 显式声明 | 不需要 |
| 精度转换方案 | 构建期或运行期策略 | Kernel Harness；转换计算由 KernelUnit 执行 | 策略需要语义 |

也就是说，融合感知（fusion-aware）是 Kernel Harness 的属性，不是引擎的属性。把它放回引擎，等于把易变的东西放回稳定层，会退回 TVM 的路线。

需要同时强调 P2 和 P15 是一对：只有 P2 没有 P15，结论是"什么优化都做不了"；只有 P15 没有 P2，引擎会重新长成编译器。

检查：引擎不应存在 `passes/` 目录；Kernel Harness 必须有 `partition/`、`layout/`、`mem/` 三个模块，且各自有单元测试。

## P16 优先复用厂商库

KernelUnit ABI 必须能容纳厂商库（cuDNN、cuBLAS、CUTLASS 实例化产物）作为一等公民（`kind: vendor`）。Agent 的第一职责是判断哪里该用库、哪里需要自己写，第二职责才是自己写。

理由是：公开数据表明，Agent 生成的 kernel 对上经过调优的库普遍低于 1 倍。对于一个孤立的 3×3 conv，cuDNN 的调优积累是压倒性的，强行要求 Agent 自己写，等于把项目成败绑在"超过 NVIDIA"这个不现实的赌注上。

反过来说，对于 C2f 这类融合块（split、三个 conv、concat），没有任何库提供现成 kernel。这里的基线是"三个独立 cuDNN conv 加三次写回"，Agent 赢的是融合本身，不是卷积。

所以 Agent 的价值分布是：

```
孤立算子性能      库更强         Agent 应选择库
融合边界决策      无人可做       Agent 的唯一价值来源
融合内部实现      无人可做       Agent 自己写
端到端调度        引擎提供       Agent 决策
```

检查：kernel 生成流程中必须有"先评估 vendor 方案"的步骤，且该判断需要记录在产物中（例如 manifest 里注明为什么没有采用库）。

## 附录 B 原则冲突时的裁决顺序

原则之间会冲突。冲突时按下列顺序裁决，序号靠前的优先：

1. P2 引擎不依赖模型语义。这是硬约束，不与其他原则妥协。
2. P15 需要语义的优化放在 Kernel Harness。它与 P2 配对，缺了它 P2 会导致无法做任何优化。
3. P6 每个 KernelUnit 必须有参考实现和降级路径。正确性优先于性能。
4. P7 错误必须定位到 node、slot 和索引。不可诊断的系统长期会失去 P6。
5. P3 跨边界信息显式声明，P9 硬件特化声明与检查。长期成本的主要来源。
6. P4 稳定性分级，P14 编译与代码生成离线。决定项目能否跨越第二代硬件。
7. P5 编排由确定性程序生成。决定 Agent 闭环的稳定性。
8. P16 优先复用厂商库。决定第一版能否跑赢基线，也决定工作量是十个 kernel 还是三十个。
9. P1、P8、P10、P11、P12、P13。工程纪律。

任何"为了性能指标而模糊契约"的提案，实际上是用第一优先级换取第九优先级的东西。
