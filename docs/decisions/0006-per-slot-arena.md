# 决策 0006 每个 in-flight 槽位独立 arena

- 状态：已接受
- 时间：2026-10

## 背景

一个 session 可能同时有多次 run 在执行，例如多路视频或批处理。它们共用显存，分配策略有三种：

- 全局共享 arena 加锁或原子操作。
- 全局共享 arena 加无锁分配器，例如 caching allocator。
- 每个 in-flight 槽位一块固定 arena，本方案。

## 决定

采用第三种。设置 `max_inflight` 个槽位，每个槽位有独立 arena，大小等于 plan 的 arena 表达式。总显存为 `max_inflight` 乘以单槽位大小。

## 理由

| 方案 | 无锁 | 碎片可控 | 偏移确定（graph 的前提） | 并发正确性 |
|---|---|---|---|---|
| 全局共享加锁 | 否 | 是 | 是 | 需谨慎 |
| 无锁分配器 | 部分 | 否 | 否，地址随时间变化 | 需谨慎 |
| 每槽位独立 arena | 是 | 是 | 是 | 天然正确 |

决定性理由是 CUDA Graph 要求捕获时的指针在重放时依然有效。caching allocator 的地址会随分配历史变化，直接摧毁 graph 的可用性。第三种方案是唯一同时满足无锁和偏移确定的选择。

## 后果

正面效果是零锁、零碎片、偏移确定、对 graph 友好，且一次 run 的越界不会踩到另一次。

负面效果是显存占用随槽位数线性增长。YOLO 单次 arena 约 80 MB，四个槽位是 320 MB。

这是有意的取舍：用显存换取确定性和实现简洁。在推理场景里显存通常不是瓶颈，模型本身占大头，而确定性是刚需。

## 缓解

`max_inflight` 是创建 session 时的参数，由应用按并发度设置。默认值为 1，多路场景按需调大。
