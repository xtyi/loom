# 决策 0005 结构由程序生成，kernel 由 Agent 生成

- 状态：已接受
- 时间：2026-10

## 背景

"Agent 协同设计"很容易滑向"让 Agent 生成一切"。但一个 YOLO plan 约有 200 个 slot、40 个 node、600 多个数字，包括偏移、stride 和连线。让 LLM 生成它，出错率接近 100%，而且错误是静默的：连线错了不会报错，只会算错。

## 决定

Agent 的自由度限制在两类产物：

1. 融合分组建议，格式为 `FusionDecision`，经 D1 到 D6 结构校验。
2. 单个 KernelUnit 的实现，在固定脚手架内填写。

plan 的连线、slot、偏移、stride 和 variant 必须由确定性程序生成，即 Kernel Harness 的 `emit/`，禁止调用 LLM。

## 理由

| 产物 | 需要创造力 | 有客观判据 | 出错成本 |
|---|---|---|---|
| 融合分组 | 有一定需要 | 有，实测性能 | 中，可以重来 |
| kernel 实现 | 有，涉及分块、访存、硬件机制 | 有，正确性与速度 | 中，可以重来 |
| plan 连线 | 没有，属于机械变换 | 没有，错了也能跑 | 高，属于静默错误 |

判断标准是：LLM 应当放在有客观判据的位置。plan 连线没有客观判据，跑起来就是一个错误答案，而你不知道。

## 后果

正面效果是 plan 生成零错误、可单元测试、可 diff、可复现；Agent 的上下文需求小，只看一个组而不看全图；失败被限制在最小的盒子里。

负面效果是 Kernel Harness 需要一套真正的图变换实现，这不是写几个 prompt 就能完成的；Agent 也无法做跨节点的非常规编排。

## 缓解

如果将来需要更自由的编排，正确做法是给 plan 格式增加表达能力，例如更灵活的 stream 用法和视图 slot，然后让确定性合成器去使用这些能力，而不是让 LLM 直接写 plan。
