# 决策 0004 plan 是显式编排，引擎不改写语义

- 状态：已接受
- 时间：2026-10

## 背景

plan 中 node 的顺序、所属 stream 和缓冲区绑定，有两种确定方式：

- 显式：由生成器写死，引擎照做。
- 隐式：给引擎一张依赖图，由它做拓扑排序、并发发现和重排。

## 决定

采用显式。引擎不得做任何语义改写，包括融合、布局重排、代数化简和算子替换。

引擎可以做的只有数据流层面的簿记：liveness、别名校验、无副作用时的死码删除、依赖推导与事件插入、CUDA Graph 捕获。

## 理由

第一，确定性。拓扑排序有多种合法结果，按 node id 升序只有一种。

第二，可归因。出错时能精确对应到"第 17 个 node"，而不是"引擎优化后的某个节点"。

第三，并发可审计。多流重叠是性能关键决策，应当由能看到全图和 profile 数据的 Kernel Harness 与 Agent 决定，而不是引擎的启发式决定。

第四，与 00 文档 0.5 节的边界一致。自动发现并发需要语义，例如共享资源与数值影响。

## 后果

正面效果是执行完全可预测，plan 的 diff 能反映所有决策，调试简单。

负面效果是并发决策的责任落到 plan 生成侧。如果生成器偷懒，把所有 node 都放在 stream 0，性能会差。好在这个问题是可见的，也可以优化。

## 数据依赖仍由引擎推导

node 之间的数据依赖，包括 RAW、WAW 和 WAR，由引擎从 slot 的读写集合自动推导。这是纯数据流性质，不需要语义。plan 中的 `after` 只用于声明额外的、非数据的顺序约束。

因此 Agent 写不出竞争条件，引擎会修正或拒绝。
