# 决策 0001 不做图编译与算子生成

- 状态：已接受
- 时间：2026-10

## 背景

AI Compiler 用二十年时间试图解决"模型图到可执行程序"的自动转换。核心困难在于图里只有"做什么"，没有"怎么做"，而 GPU 上的一个算子是一整个程序，涉及迭代空间、分块、并行、同步和流水。

TVM 用 Iteration Space 加 Schedule 原语表达这件事，在 SIMT 时代有效。Hopper 引入 TMA、WGMMA、warp group 和 warp specialization 之后，这套抽象既无法表达新机制，也难以统一新旧机制。PyTorch 则退化为模板加规则融合加 aten 兜底。两者都没有解决问题，只是绕开了它。

## 决定

引擎不做图编译优化，不做算子生成，不做算子融合。这些能力全部外置到 Kernel Harness 与 Agent。

此处“图编译”指模型语义变换与 kernel 代码生成。执行 DAG 的结构校验、确定性拓扑排序、依赖同步与 schedule 校验属于运行时；它们不需要理解算子数学语义。边界更新见决策 0004 与 0009。

引擎只做三件事：运行时资源管理（内存、并发、加载）、正确性保证（校验、降级、诊断）和执行编排（执行显式 plan）。

## 理由

引擎若不承担代码生成，就不会随硬件代际变化，见 00 文档 0.4 节。引擎规模也因此有上限，功能需求不会无限膨胀。同时，它与"程序由谁生产"解耦，人工、Agent 和未来的编译器都能接入。

## 后果

正面效果是引擎稳定、体积小、启动快，且不随硬件换代重写。

负面效果有三个：每个模型与硬件组合都需要一次性工程投入，这是最高优先级风险，见 12 文档；端到端性能依赖外部的融合决策质量；没有开箱即用的图优化，新模型不能白得性能。

## 备选方案

方案一，做带融合感知的轻量编译器。它能在未知模型上直接获得 20% 到 40% 的性能，但会重新长出 TVM 的复杂度。否决，因为它只是半个编译器，长期一定会走向失败的那半个。

方案二，只做 kernel 库加调度器。放弃通用性，价值上限低。

方案三，即本方案。把代码生成完全外置，引擎只保留稳定部分。
