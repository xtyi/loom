# 决策 0003 用 C ABI 加 dlopen，不做源码级 JIT

- 状态：已接受
- 时间：2026-10

## 背景

外部 kernel 有三种接入形态：

1. 源码，引擎内置编译器，例如 NVRTC 或 LLVM，在运行时编译。
2. IR 或 DSL 程序，引擎内置对应的运行时编译器。
3. 二进制 `.so`，预编译，`dlopen` 加载，按 C ABI 调用。

## 决定

采用第三种。运行时的依赖中不允许出现任何编译器前端或后端，见 01 文档 P14。

## 理由

| 方案 | 优点 | 缺点 |
|---|---|---|
| 源码加 NVRTC | 灵活，可以按 shape 编译 | 需要 nvcc 或 NVRTC，编译耗时秒级，依赖工具链，难以审计，把代码生成拉回运行时 |
| IR 加 DSL runtime | 可以做运行期特化 | 引入 Triton 或 LLVM 依赖，`ldd` 会拉进几十 MB，版本耦合严重 |
| 二进制 `.so` | 依赖最小，启动最快，可签名，可审计，可复现 | 不支持运行期生成 |

三条决定性理由：部署环境可能没有编译器，例如车载、嵌入式和受限容器；供应链安全要求产物可签名、可哈希，见 01 文档 P12；可复现性要求同一产物永远行为一致，而源码 diff 无法保证这一点。

## 后果

正面效果是运行时极小，依赖只有 libc 与 CUDA 或 HIP runtime；启动快，加载时间与模型规模无关；产物可签名、可审计、可回滚。

负面效果有两个：形状特化必须在离线完成，由 plan 的 variant 表达；没有运行期 JIT 兜底，域外形状只能降级到 ref 或拒绝。

## 缓解

用 coverage 显式声明覆盖域并配置 `fallback_ref` 策略，见 06 文档第 3 节。同时用符号化 kernel 覆盖全域，使"未特化"不等于"不可用"，见 05 文档第 5.1 节。
